## 2. つまずきのパターン(8種類)

アプリでは、各問題に下の **つまずきタグ** を付け、間違えた問題がどのパターンに偏っているかを集計します。

### ① 問題文・用語の読解(タグ:`reading`)
**最も特徴的なパターンです。** 解き方以前に、問題文の言葉で止まっています。
- 「問題文を理解することがまず難しい」(ハッシュ関数 f(x) = x mod 7 + 1)
- 「問題文や単語が全く理解できない」(相補演算、XOR)
- 「問題文と図の理解がそもそもできない」(階乗の流れ図)
- 「問題文や単語をそもそも理解できない。ハッシュ表やハッシュ関数が分からない」

→ **アプリへの反映**:すべての問題に「問題文を言い換える」ボタンを付ける。問題文中の用語をタップすると用語集が開く。

### ② 記号・図の読み方(タグ:`symbol`)
- 論理回路の記号(なぜNANDと分かるのか)
- 流れ図のループ端「n : M, −1, 1」、`←`、ひし形のYes/Noの向き
- 状態遷移図の「入力/出力」ラベル、ベン図の斜線
- `div` と `mod`

→ **アプリへの反映**:「記号辞典」画面を作る。問題やトピックから該当記号へリンクする。

### ③ 前提知識の抜け(タグ:`prerequisite`)
問題を解く途中で、土台の知識に戻る質問が多いです。
- 真理値表を1から(XORの問題の途中で)
- 16進数とは/文字コードとは(パリティの問題の途中で)
- ポインタとは(リスト構造の問題の途中で)
- バブルソートとは/二分探索とは/SSIDとは/XMLとは

→ **アプリへの反映**:各トピックに「前提トピック」を設定する。間違えたとき「この問題の前提:16進数 → 2進数」のように戻り先を提示する。

### ④ 「なぜ」が腹落ちしないと進めない(タグ:`why`)
答えを覚えるより、理由を理解しようとする学び方です。これは強みです。
- 再帰で、なぜ小さい値から呼び出す必要があるのか
- デジタル署名が、なぜ証明になるのか → 公開鍵で読めるなら改ざんできるのでは?
- `n XOR 11111111` で、なぜ全ビットが反転するのか
- `j ← j div 2` の意味/ループの初期値・増分・終値がなぜその値なのか
- バブルソートで、なぜ4から比べるのか

→ **アプリへの反映**:解説に「なぜ?」セクションを独立させる。「なぜ問題」(理由を問う選択問題)を問題タイプとして用意する。

### ⑤ 似た概念の混同(タグ:`confusion`)
- キャッシュメモリ と フラッシュメモリ
- フォワードプロキシ と リバースプロキシ
- SDN と NFV
- インフラ/プラットフォーム と バックエンド
- 1台に同居 と 仮想化/VM と コンテナ
- バイトコード と TypeScript/コンパイル と トランスパイル
- ビッグデータ/DWH/データレイク
- SSID と チャネル
- 表のアクセス時間 と 平均アクセス時間
- パッチ と バッチ

→ **アプリへの反映**:「比較カード」画面を作る。混同ペアを並べて、違いの一言と比較表を見せる。

### ⑥ ひっかけに乗る(タグ:`trap`)
誤答の理由がはっきりしている問題が多いです。

| 問題 | 選んだ答え | ひっかかった理由 |
|---|---|---|
| 遷移確率の表 | a+d=1 | 「正しく伝わる確率」を足せば1と考えた |
| 論理回路(NAND×4) | AND の動きの選択肢 | NOT+NOTの打ち消しを見落とし、逆を選んだ |
| フラッシュメモリ採用の理由 | 処理性能の向上 | 「新しい技術=性能アップ」と連想 |
| プリンタへのジョブ割当 | 順番に回した結果 | 「空いた装置に割り当てる」を読み落とした |
| 流れ図(階乗)の空欄 | n < M | 「続ける条件」と「抜ける条件」を逆にした |
| 2段階の線形探索の平均比較回数 | n/m | 「平均なので半分」と「2段階目」が抜けた |
| DMA | パイプラインの説明 | CPUの高速化技術どうしを混同 |
| 無線LANのチャネル | 全APを同じチャネル | 揃えるべきはSSIDだった |
| ハッシュの衝突(ASCII) | a と i | 文字の共通点(母音)で選んだ |

→ **アプリへの反映**:誤答ごとに「この選択肢を選んだなら、こう考えたのでは?」を表示する(教材データの `wrongReasons`)。

### ⑦ 計算・式の立て方(タグ:`calc`)
- 平均アクセス時間の式、2台のCPUで等しくなるヒット率
- 縮退運転(合計を固定して残り台数で割る)
- MIPS・CPI・単位変換
- 線形計画法の頂点の連立方程式

→ **アプリへの反映**:数値入力問題を用意する。公式カードを各トピックに付ける。

### ⑧ 手順のトレース(タグ:`trace`)
- 流れ図、再帰、バブルソート、状態遷移、div/modのループ
- 解説で毎回効いているのは「小さい数を入れて表を書き、1行ずつ追う」方法

→ **アプリへの反映**:トレース系の問題には、解説にトレース表を必ず入れる。

## 3. 分野別の弱点度

セッションでの質問量・深掘り量・誤答をもとにした推定です。アプリの「弱点」初期値に使います(実際の演習結果で更新)。

| 分野 | 弱点度 | 根拠 |
|---|---|---|
| アルゴリズム・流れ図(トレース、ループ指定、再帰、div/mod) | ★★★ | 問題数最多。「図が読めない」発言あり。誤答2問 |
| 論理演算・ビット演算(真理値表、XOR系、2の補数) | ★★★ | 3セッションにまたがる。深掘り質問が最多 |
| データ表現(2進小数、16進、パリティ、文字コード) | ★★★ | 1問に4回の追加質問 |
| ハッシュ | ★★☆ | 3セッションで出題。用語レベルからつまずき |
| セキュリティ(署名、暗号、WAF、SQLi) | ★★☆ | 署名で3回深掘り。WAFは理由が分からず質問 |
| メモリ・CPU(キャッシュ、フラッシュ、DMA、MIPS) | ★★☆ | 誤答2問。混同が多い |
| ネットワーク(無線LAN、プロキシ、SDN、IPv6) | ★★☆ | 誤答1問。混同が多い |
| クラウド・基盤(IaaS等、仮想化、コンテナ) | ★☆☆ | 自分の言葉で要約できている。理解は良好 |
| IT用語(実務) | ★☆☆ | 要約→確認のサイクルで理解できている |

## 4. 学び方の特徴(アプリの体験設計に反映)

1. **自分の言葉で要約して確かめる**
   「モジュールとプログラムを合わせてコードと呼ぶってこと?」「送信者は〜ということ?」のように、理解を言い直して確認しています。
   → **「自分の言葉で説明する」モード**を作る。説明を書いた後に模範解答と比べ、自己採点する。

2. **図を強く好む**
   ほぼ全セッションで図を依頼しています。
   → トピックごとに図(Mermaid など)を持てるデータ構造にする。

3. **たとえ話で定着する**
   キャッシュ=机、主記憶=倉庫、API=レストランの店員、署名=ハンコと照合シート、など。
   → トピックに「たとえ」欄を設け、カードの最初に見せる。

4. **スマホで隙間時間に、PCでじっくり**
   → 1問1画面、片手操作できるサイズ。PCでは2カラム(左にマップ、右に本文)。
